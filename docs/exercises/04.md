# Exercise 04: Merge, pull request, and conflict

**Mode:** Submitted result and PR.

## Situation

Two developers changed the same borrowing-policy method. One allows students to borrow three books; the other allows faculty to borrow five. The release needs both requirements.

## Start

Run from the launcher:

```text
python3 lab.py start 04
```

Open the workspace path printed by `start`. The workspace starts on `result/ex04` at `lab-v1/ex04/start`, which already contains the student limit. The faculty work is at `lab-v1/ex04/faculty`. Their competing edits are intentional.

## Inspect this exercise

Inside the workspace:

```text
git log --oneline --graph --decorate HEAD lab-v1/ex04/faculty
```

For variant B, use `lab-v1/ex04-b/faculty` instead.

## Task

See the [starting commit graph](../GRAPHS.md#exercise-04-two-policy-edits) to compare the two policy histories before integrating them.

The helper is a **tag naming a commit**, not a local branch. Git can merge a tag directly with `git merge TAG-NAME`; use the faculty tag for your assigned variant. You do not need to create a helper branch first.

1. Publish the untouched `result/ex04` branch to your fork. Create and switch to `feature/ex04` from that starting point.
2. Merge the faculty helper history into the feature branch. Resolve the policy conflict so student and faculty limits both survive. Complete the merge and inspect the resulting graph.
3. Check the feature result, then publish `feature/ex04` and open a PR **inside your own fork**, from `feature/ex04` into `result/ex04`. Describe the conflict decision and checks. Merge with **Create a merge commit**.
4. Fetch the merged result, update your local `result/ex04`, and run the check again.

## Success conditions

- Student limit: **3**. Faculty limit: **5**. Loans remain 14 days, overdue fees remain 100 per day, and search remains case-sensitive.
- Both prepared policy histories are ancestors of the result; resolving the conflict does not discard either requirement.
- The PR is merged into `result/ex04` in your fork. No conflict markers or uncommitted changes remain.

## Check

Before publishing the feature branch, run from the launcher using the exact workspace path printed at start:

```text
python3 lab.py check 04 --repo "/PATH/TO/YOUR/WORKSPACE"
```

After merging the PR on GitHub, run inside the exercise workspace with a clean working tree:

```text
git fetch origin
git switch result/ex04
git merge --ff-only origin/result/ex04
```

Then repeat the launcher check against that same workspace. Read the evaluated branch and commit ID: the first check evaluates `feature/ex04`; the second evaluates the fetched, merged `result/ex04`. If the fast-forward is rejected, inspect the two histories rather than forcing an update.

The local check validates the integrated behavior and history at current `HEAD`; it does not create or verify a GitHub PR. Check the PR base repository, base branch, head branch, merge method, and merged state separately. A feature-branch PASS alone does not complete submission.
